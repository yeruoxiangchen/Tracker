# AutoDL D74：RTX PRO 6000 四卡迁移、配置、续训与远程开发指南

日期：2026-08-14

适用任务：`ProObjaverse 官方 SLat Train2000` 从当前四卡 checkpoint 继续训练、评测和开发

目标机器：D74，`RTX PRO 6000 96GB × 4`，约 100 CPU 核、480GB RAM，30GB 系统盘、50GB 免费本地数据盘、最多再扩 107GB

## 1. 直接结论

### 1.1 镜像怎么选

首选 AutoDL 的官方/基础框架镜像，不优先选来历不明的社区镜像。选择顺序如下：

1. AutoDL 列表中的 `PyTorch/2.12.1/3.12 (Ubuntu 22.04)/13.0`。这就是本任务当前首选。
2. 若没有上述组合，选 `PyTorch 2.10.x + CUDA 13.0 + Python 3.10/3.12`。
3. 再没有时，选 `Ubuntu 22.04 + Miniconda + CUDA 13.0 devel`，然后按本文建立环境。
4. 不选当前项目原来的 `PyTorch 2.4 + CUDA 12.1` 镜像。它没有 RTX PRO 6000 所需的 Blackwell `sm_120` 完整支持。
5. CUDA 13.2 虽然与主机驱动匹配，但当前 PyTorch 对 CUDA 13.0 的稳定组合和第三方扩展兼容性更好；不要仅因为页面写着“CUDA ≤ 13.2”就强行选 13.2。

RTX PRO 6000 96GB 是 Blackwell GB202、计算能力 12.0。PyTorch 的 CUDA 13.0 Linux 包包含 Blackwell 12.0/PTX 支持；xFormers 0.0.33 起也加入了 Blackwell CUTLASS attention。当前机器上的旧 `flash-attn 2.7.0.post2` wheel、`xformers 0.0.27.post2` 和 `torch 2.4.0+cu121` 不能复制到新机继续用。

社区镜像只在以下条件全部满足时考虑：

- 发布者和来源可核验；
- 明确注明 RTX 5090/RTX PRO 6000、`sm_120` 已实测；
- PyTorch 是 CUDA 12.8 或 13.x 的 Blackwell 版本；
- 能现场通过本文的 xFormers、spconv、四卡 NCCL 和两步项目 smoke；
- 镜像中没有不明 SSH key、代理、token 或启动脚本。

即使社区镜像通过，也只把它当作节省安装时间的起点。完成验证后，保存自己的私有镜像，例如 `reconvggt-pro6000-sm120-v1`。

### 1.2 是否扩容本地数据盘

第一阶段不必扩容。

- 168GB Train2000 缓存无论如何都放不进 50GB 本地盘；即使追加 107GB，总容量约 157GB，仍然不够。
- 该缓存应持久保存在 AutoDL 文件存储，再在每次开机时复制到 480GB RAM 的 `/dev/shm`。
- 50GB 本地数据盘用于新 checkpoint、日志、临时文件和编译缓存，当前任务够用。
- 如果后续希望把 Dev64、多个评测输出和更多 checkpoint 都留在本地 SSD，可再扩 50～80GB；扩容不是开始训练的前置条件。

### 1.3 当前真正需要迁移什么

截至本次检查，当前 step4000 阶段仍在运行，日志快照已到 step3650。必须等 `step_004000.pt` 和 `stage_report_step_004000.json` 都完整生成后，再从 D74 启动续训。

| 内容 | 当前大小 | 首次续训是否必需 | 说明 |
|---|---:|---|---|
| Train2000 cache | 168GB | 是 | 放文件存储，运行时复制到 RAM |
| ProObjaverse 5K 的 `lh-slats` | 1.5GB | 是 | manifest 的 target 绝对路径会访问它 |
| `step_004000.pt` | 约 580MB | 是 | 只复制最终完整 checkpoint |
| `stage_report_step_004000.json` | 数 MB | 是 | 确认上阶段完整完成 |
| decoder audit 的 `report.json` | 46KB | 是 | 不必复制整个 958MB audit 目录 |
| Native-SS report | 299KB | 是 | 训练证据绑定 |
| Native-SS `step_002000.pt` | 553MB | 是 | `load_ss_evidence` 会检查文件存在及 SHA256 |
| stock freeze JSON | 1.8KB | 是 | 训练冻结合同 |
| Stable-X 模型 Hugging Face cache | 3.1GB | 建议 | 可离线直接复用，省去重新下载 |
| Dev64 cache | 5.4GB | 后续评测需要 | 四卡训练时无空闲 GPU，可稍后复制 |
| ProObjaverse 30K 原始数据 | 约 118GB | 否 | step4000 续训不读取，不要先搬 |
| 整个 `/home/zjr/Tracker` | 约 800GB | 否 | 含大量 outputs；不能整仓复制 |

代码也不能只 `git clone`：当前续训代码包含未提交修改和未跟踪的新文件。正确方法是“Git 基线（可选）+ 指定代码目录的工作区覆盖同步”，不要 `scp -r /home/zjr/Tracker`。

### 1.4 预计费用提醒

在提交订单前看最终费用明细。若页面的 `￥5.98/时` 是每卡价格，四卡就是约 `4 × 5.98 = ￥23.92/时`，不是整机 ￥5.98/时；以付款页显示为准。

168GB 传输和环境安装都不需要 GPU。如果实例支持无卡模式，可用无卡模式做初始上传和普通配置，但无卡模式会释放 GPU，重新开四卡时可能没有库存。若必须锁住这台 D74，就先开四卡，但要并行完成传输和兼容性 smoke，避免卡空转。

## 2. 开机前准备

### 2.1 初始化同地区文件存储

在 AutoDL 控制台进入“文件存储”，初始化 D74 所在地区。实例开机后应该出现：

```bash
df -h /root/autodl-fs
```

AutoDL 文件存储默认总额度 200GB，前 20GB 免费，超过部分按日计费。当前最小迁移集合约 174GB，接近但仍低于 200GB。不要把无关 30K 数据和历史输出一起放进去。

### 2.2 准备 Windows SSH key

在本机 Windows PowerShell 中执行：

```powershell
ssh-keygen -t ed25519 -C "autodl-d74" -f "$env:USERPROFILE\.ssh\id_ed25519_autodl_d74"
```

把 `.pub` 公钥按 AutoDL 控制台说明添加到实例；私钥留在 Windows，不要复制到 D74，也不要发到聊天或仓库。

### 2.3 记录实例 SSH 信息

实例启动后，控制台会给出类似下面的命令：

```text
ssh -p <端口> root@<区域主机名>
```

后文使用：

```text
AUTODL_HOST=<区域主机名>
AUTODL_PORT=<SSH端口>
```

主机名、端口不要猜，直接复制控制台当前值。

## 3. 开机后的前 10 分钟

先在 AutoDL Web 终端或 SSH 终端运行以下只读检查：

```bash
date -u
nvidia-smi
nvidia-smi topo -m
free -h
df -h / /root/autodl-tmp /root/autodl-fs /dev/shm
lsb_release -a 2>/dev/null || cat /etc/os-release
python --version
nvcc --version 2>/dev/null || true
```

必须看到：

- 4 张 RTX PRO 6000，每张约 96GB；
- 总 RAM 约 480GB；
- `/dev/shm` 足以容纳 168GB 缓存，理想值应明显大于 200GB；
- `/root/autodl-tmp` 是 50GB 本地数据盘；
- `/root/autodl-fs` 已挂载。

如果 `/dev/shm` 只有几 GB，不要开始复制缓存或训练，先联系 AutoDL 确认容器共享内存配置。

需要下载 Python 包或 GitHub/Hugging Face 文件时，可在当前安装终端尝试 AutoDL 学术资源加速：

```bash
source /etc/network_turbo
```

它不是 OpenAI/ChatGPT 的专用代理，也不保证 Codex 可访问。环境装完后不用把它写进全局 shell 配置。

## 4. 从 Windows 用 VS Code 连接 D74

### 4.1 配置 OpenSSH

编辑 Windows 文件：

```text
C:\Users\<你的Windows用户名>\.ssh\config
```

加入：

```sshconfig
Host autodl-d74
    HostName <区域主机名>
    User root
    Port <SSH端口>
    IdentityFile C:/Users/<你的Windows用户名>/.ssh/id_ed25519_autodl_d74
    ServerAliveInterval 30
    ServerAliveCountMax 6
    TCPKeepAlive yes
```

在 PowerShell 验证：

```powershell
ssh autodl-d74
```

### 4.2 VS Code 操作

1. Windows 本机安装 VS Code 扩展 `Remote - SSH`。
2. `Ctrl+Shift+P`，选择 `Remote-SSH: Connect to Host...`。
3. 选择 `autodl-d74`，远程系统选 Linux。
4. 第一次连接后打开 `/root/Tracker`。
5. Python 扩展、Codex 扩展如果显示“Install in SSH: autodl-d74”，安装在远程端。
6. Python 解释器选择该镜像默认环境的 `/root/miniconda3/bin/python`。

VS Code 断开会终止普通前台终端进程。正式训练必须放在 `tmux` 中，不要依赖 VS Code 终端一直在线。

## 7. 将 Train2000 cache 放进 RAM

文件存储是持久副本，但 AutoDL 官方也说明其 IO 性能一般。训练前将 168GB cache 复制到 `/dev/shm`：

```bash
set -euo pipefail
PERSIST=/root/autodl-fs/data/zjr
HOT=/dev/shm/proobj_train2000_cache_20260813

mkdir -p "${HOT}"
time rsync -a --whole-file --info=progress2 \
  "${PERSIST}/proobjaverse_official_slat_train2000_20260813_v1/cache_train2000_protocol2128_views8_v1/" \
  "${HOT}/"

du -sh "${HOT}"
```

从文件存储复制到 RAM 的时间取决于共享存储当时的吞吐：100MB/s 约 29 分钟，300MB/s 约 10 分钟，500MB/s 约 6 分钟。第一次实际执行的 `time rsync` 才是这台实例的基准。

RAM 内容在关机、重启、异常释放后消失，这是预期行为；持久副本仍在 `/root/autodl-fs`。

### 12.4 使用 Windows 本地代理的 SSH 反向隧道

假设 Windows 上 Clash/其他代理的 HTTP mixed port 是 `127.0.0.1:7890`，在 SSH config 增加一个单独别名：

```sshconfig
Host autodl-d74-proxy
    HostName <区域主机名>
    User root
    Port <SSH端口>
    IdentityFile C:/Users/<你的Windows用户名>/.ssh/id_ed25519_autodl_d74
    ServerAliveInterval 30
    ServerAliveCountMax 6
    RemoteForward 17890 127.0.0.1:7890
    ExitOnForwardFailure yes
```

用 VS Code 或 PowerShell 连接 `autodl-d74-proxy` 后，D74 的 `127.0.0.1:17890` 会转发到 Windows 的 `127.0.0.1:7890`。

在 D74 的 Codex 专用终端中测试：

```bash
curl -x http://127.0.0.1:17890 \
  -sS -o /dev/null -w 'proxied api HTTP %{http_code}\n' \
  --connect-timeout 10 https://api.openai.com/v1/models
```

若通，再只在 Codex 当前 shell 设置：

```bash
export HTTP_PROXY=http://127.0.0.1:17890
export HTTPS_PROXY=http://127.0.0.1:17890
export NO_PROXY=localhost,127.0.0.1
codex login --device-auth
codex
```

重要限制：

- OpenAI 官方 Codex 环境变量文档没有把 `HTTP_PROXY`/`HTTPS_PROXY` 列为 Codex 稳定专用配置，因此这是依赖标准网络栈的实测方案，不作无条件保证。
- Windows 休眠、关机、VS Code/SSH 断开后，反向隧道会消失，D74 上的 Codex 网络也会中断。
- 不要把 Windows 代理端口暴露到公网；`RemoteForward` 保持远端 loopback 即可。
- 不要把代理变量写进训练 tmux 或全局 `.bashrc`。训练本身不需要 OpenAI 网络，代理中断不应影响训练。
- 若代理做 TLS 中间人，Codex 官方支持通过 `CODEX_CA_CERTIFICATE` 指定额外 CA；不要用关闭证书验证来绕过。

## 14. 常见故障与处理

### 14.1 `no kernel image is available for execution`

某个二进制扩展不含 `sm_120`。先分别运行 PyTorch、xFormers、spconv 门禁定位。不要通过降驱动或反复重启掩盖问题。

### 14.2 `flash_attn` 导入或运行失败

当前旧 wheel 是为 torch2.4/cu12 构建，不能搬。D74 默认使用 `ATTN_BACKEND=xformers`。只有经过 Blackwell 实测的新版 flash-attn 才能替换。

### 14.3 spconv NVRTC 报错

停止长训。优先找可审计、已经在 RTX PRO 6000 上通过真实卷积的构建；源码构建涉及 cumm、CUDA 13 和 C++17 兼容问题，不能只看到 `pip install` 成功就认为可用。

### 14.4 文件存储有空间却提示磁盘满

检查容量和 inode：

```bash
df -h /root/autodl-fs
df -i /root/autodl-fs
```

AutoDL 文件存储默认 inode 上限为 20 万。当前 2000 对象 cache 通常不会触顶，但不要继续堆大量无关小文件。

### 14.5 VS Code 断开后训练停了

说明训练没有在 tmux 中，或 tmux 里的 shell 已退出。正式命令先 `tmux new -s ...`，再启动训练。

### 14.6 Codex 浏览器登录成功但对话失败

浏览器登录和 D74 的持续网络是两件事。重新测试 `https://api.openai.com/v1/models`；若走 Windows 反向隧道，确认 `ssh autodl-d74-proxy` 仍在线、Windows 代理 7890 仍监听。

## 15. 一页执行顺序

1. 控制台初始化 D74 所在地区的文件存储。
2. 镜像优先选 `PyTorch/2.12.1/3.12 (Ubuntu 22.04)/13.0` 官方镜像。
3. Windows 建 SSH key，配置 `autodl-d74`，VS Code Remote-SSH 连入。
4. D74 先检查四卡、480GB RAM、`/dev/shm`、本地盘和文件存储。
5. 当前服务器用 rsync 白名单同步代码，不能整仓复制。
6. 当前服务器在 tmux 中把 168GB cache、1.5GB targets、Native-SS checkpoint、三个证据 JSON 和 HF cache 传入文件存储。
7. 等当前 step4000 完整完成，传 `step_004000.pt` 与 stage report，并校验 SHA256。
8. D74 复用镜像 `base`，核对 torch2.12.1/cu130，安装 Blackwell xFormers 和待验证 spconv。
9. 依次通过 PyTorch、xFormers、spconv、四卡 NCCL 门禁。
10. 文件存储中的 168GB cache 复制进 `/dev/shm`，建立 `/data/zjr` 兼容软链接。
11. 从 step4000 跑到 step4002 smoke。
12. smoke 通过后，在 tmux 中按四卡、global batch 8 续训到 step10000。
13. 新 checkpoint 定期从本地盘同步到文件存储。
14. Codex 优先设备码登录；不能直连时使用 Windows 代理的 SSH `RemoteForward`。
15. 环境完全验证并清除凭据后保存私有系统镜像。
